# The vernaculars, and two things that are not languages

## Who is reading

**Someone who does not read Chinese, in a language of their own.** That is the
premise the whole of this file follows from, and it has two halves that are
easy to hold only one of.

The first half is why hanzi and pinyin exist in the output at all: the reader
has come to a Chinese art, the things in it have Chinese names, and a name
withheld is a thing they cannot look up, quote or ask anybody about. The
second half is why nothing they *operate* is in Chinese: a glyph they cannot
pronounce is not a label, it is a picture of one.

**How many languages there are is a state and not a design.** Two today,
English and Italian; Spanish when the engine has stopped gaining boards — see
`ROADMAP.md`. Nothing here may be written as though the set were closed at
two, and the honest test of anything added to the catalogs is what a third
language would cost to write: a gloss beside a name costs one line, a
paragraph of argument costs a translator who has to follow the argument.
That asymmetry is the reason the derived half of a surface is worth building
and the written half is worth keeping short.

**English is the default and the fallback of last resort**, which is a
different claim from being the better language: a surface that cannot
determine a locale must still produce readable text, and English is what it
produces. `LOCALES` in `packages/i18n/src/locale.ts` is the list, and
`apps/web/test/docs.test.ts` holds this page to it.

## The engine does not localise

**Exactly as it does not interpret.** `core` returns identifiers, hanzi,
pinyin and numbers; readable text is produced at the surface, from the
catalogs in `packages/i18n`. A function in `core` that returns a translated
string is a design error: it makes the same result untestable across locales
and ties the engine to a concern belonging to whoever displays the result.

## Four kinds of string, four treatments

| | Example | Where it lives |
|---|---|---|
| **Identifier** | `xiumen`, `tianpeng`, `zhifu` | `core`. Toneless pinyin, ASCII, never translated |
| **Hanzi** | 休門, 天蓬, 值符 | `core`. Domain data — **not** a locale |
| **Pinyin** | xiūmén, tiānpéng, zhífú | `core`. Part of the name — **not** a locale |
| **Label** | "Rest Gate" / "Porta del Riposo" | `i18n`, keyed by identifier |

The two middle rows are the ones that get argued about.

**Chinese characters are not a locale.** 休門 is not the English-to-Chinese
rendering of "Rest Gate": it is the name of the gate, and an Italian reader
and an English reader both expect to see it in the palace. Hanzi travels in
the engine's output regardless of locale; the catalog supplies only the
vernacular gloss beside it.

**A name carries its reading.** Every named thing has a `pinyin` beside its
`hanzi` — tone marks, one word, `xiūmén`. A surface that prints the hanzi
prints the reading with it, because a glyph alone is, to the reader this is
built for, a shape with no sound: unsayable, unsearchable, unaskable. The
tones are what the identifiers had to drop, and they part what the identifiers
cannot — 戊 wù from 午 wǔ, 驚門 jīngmén from 景門 jǐngmén. `test/pinyin.test.ts`
checks that no name is missing one.

Where dropping the tone would collide in an *identifier*, and only there, the
tone number is kept: `jing1men` is 驚門 and `jing3men` is 景門.

A useful consequence of all this: the SVG drawing is largely
locale-independent, because the palaces contain hanzi. `plate` needs a locale
only for captions and legend, which keeps it a near-pure rendering package.

## What leads, and what stands beside

The premise at the top of this page does not contradict the rule just above
it; it bounds it, and this is the bound. Hanzi accompany the engine's output —
the palaces, the tables, the names of things — always beside a gloss, never
alone. Everything the reader is expected to *operate* or *decide from* leads
in their own language: buttons,
labels, options, the choices in a `select`. A control whose face is a glyph,
or an option that reads `zishi`, is one nobody can use on purpose, and a
`title` attribute does not rescue it — nobody hovers what they cannot
recognise.

The hanzi stands beside the word only where **what is named is Chinese**. 時辰
is; a day is not.

The same division governs the nav. An *act* is described, in the reader's own
language, so `nav.consult` and `nav.moments` differ between the catalogs. An
*instrument* is named, and a name does not translate: `Qi Men`, `Liu Ren`,
`Qi Zheng`, `Ba Zi`, `Zi Wei`, `Tai Yi` are the same string in both. The gloss
belongs in the heading of the page, which has room for it.

## Errors

`GeoError` and `ChartError` carry an English `code` (`INVALID_DATE`,
`UNKNOWN_TIMEZONE`, `INVALID_COORDINATES`, `EPHEMERIS_FAILURE`, …) plus a
`params` record. `message` is an English rendering for logs and stack traces;
a surface translates `messageKey` with `params`. Throwing localised sentences
from a pure engine reintroduces the coupling the whole design avoids.

The same holds for warnings — an ambiguous local hour, a nonexistent hour, a
polar-latitude fallback. Each is a `{ code, params }` pair, never a sentence.

Over HTTP the shape is `code` + `messageKey` + `params`. The surface
translates; nobody parses prose. See `apps/web/src/lib/server/errors.ts`.

## The catalog

No i18n framework. The message set is mostly nominal labels, and a catalog
keyed by a flat union of message keys is a `Record` and a `format` function —
what a framework would add is plural rules, gender agreement and message
syntax, none of which this set has ever needed, at the price of a runtime
dependency that must also clear AGPL compatibility. A language that needed one
of those three would be the thing that changes this, and a third language on
its own would not.

```ts
export const LOCALES = ['en', 'it'] as const;
export type Locale = (typeof LOCALES)[number];
export type MessageKey = keyof typeof en;

export const catalogs: Record<Locale, Record<MessageKey, string>> = { en, it };
```

Typing the Italian catalog as `Record<MessageKey, string>` makes a missing key
a compile error rather than a runtime fallback. A test asserts key parity in
both directions, so a stale Italian entry surfaces too. Interpolation is a
ten-line `format(template, params)`.

Dates and numbers go through `Intl.DateTimeFormat` and `Intl.NumberFormat`.
**Input formats do not follow the locale**: dates are always ISO `YYYY-MM-DD`
on every surface, so a shared URL means the same thing everywhere.

## Locale on each surface

| Surface | Negotiation |
|---|---|
| Web | path prefix `/en/…`, `/it/…`; `/` redirects on `Accept-Language`, falling back to `en`. Canonical English slugs, named for the art: `/qimen`, `/liuren`, `/bazi` |
| REST | `?lang=` query parameter, default `en`. It affects `label` fields and warning text only — identifiers, hanzi, pinyin and numbers never change |
| MCP | `lang` parameter per tool, default `en`; server instructions in English |
| CLI | `--lang`, otherwise `LC_ALL`/`LANG`/`LANGUAGE`, otherwise `en` |

The path prefix rather than a query parameter is deliberate: the interface is
public and indexable, and each language should be a distinct address. The
API keeps `lang` as a query parameter because it composes with the other chart
parameters already in the URL.

## English is free in `geo`

GeoNames stores the international exonym in the primary `name` column —
`Rome`, `Munich`, `Naples`, `Paris`, `Beijing` — which is exactly what the
English locale wants, and `countryInfo.txt` likewise carries English country
names. The expensive streaming pass over `alternateNames.zip` therefore exists
for the other vernaculars alone — Italian today — and a language added later
pays only that pass, not a second dataset.

## And the source is English

Code, comments, identifiers, error codes, documentation and commit messages.
A vernacular exists only as a locale in the catalogs of `packages/i18n`, never
in the source. That includes this directory.
